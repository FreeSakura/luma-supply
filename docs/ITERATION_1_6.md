# 1.6 目录筛选与全局价格排序

## 解决的问题

1.5 的预算和“仅有货”选项只参与图文检索。没有输入文字或图片时，网页请求图文检索会报缺少查询，小程序则返回未应用预算与库存条件的目录。用户看到的筛选项与实际结果不一致。

1.6 将预算、可售状态和排序接入目录分页。客户和商家可以不输入搜索词，直接按分类、色温、预算及有货状态选品。商品卡片标为“所选规格”价格，点击详情或报价继续使用该 SKU。图文检索保持相关度排序，并在界面明确显示，不将有限的召回候选伪装成全库价格排序。

## 接口与实现

`GET /api/catalog/page` 与旧数组接口 `GET /api/catalog/products` 新增可选参数：

| 参数 | 含义 | 默认 |
|---|---|---|
| `max_price` | 最高展示单价，非负整数分，包含上界 | 不限；0 是有效预算 |
| `available_only` | 仅选择 `stock_status=available` 的 SKU | false |
| `sort` | `newest`、`price_asc`、`price_desc` | newest |

原有 `q`、`category`、`cct_k`、`offset`、`limit` 与返回结构保留。金额仍是客户展示价；商家采购成本不会通过该接口增加暴露。

数据库先筛选符合所有条件的已上架 SKU，再通过 `ROW_NUMBER` 为每个商品选择一个规格，最后统计、排序、分页。标题匹配时优先选满足条件的 SKU 关键词命中，否则选择最低展示价规格。相同价格按商品 ID 倒序排序，保证固定数据下跨页顺序稳定；并发上下架/调价时 offset 分页不提供历史快照保证。

展示价格按管理端手动价优先，否则取初始价与有效报价较低值，再应用最新乘数并按分四舍五入。有效报价同时检查审核、上下架、删除、有效期、商家认证和账号启用状态。SQL 与已有详情定价函数通过实际数据对照测试。

数量未知仍然是原有独立业务边界：`available` 表示有货状态，不承诺满足任意采购数量，也不代表库存已经预留。采购确认继续执行原来的数量和报价版本检查。

没有新增表或改变交易状态机。窗口函数适用于项目的 SQLite 与 MySQL 8 目标配置；本轮实际验证为 SQLite，MySQL 目标部署验收仍待完成。

## 三端交互

- 网页预算输入完成、分类/色温/库存切换会重新取符合条件的结果；价格排序在全目录分页之前完成。
- 清除搜索同时重置文字、图片、裁剪、分类、色温、预算、库存和排序；注销时清除当前选灯状态及缓存。
- 客户与商家原生小程序同步目录参数、排序和清除行为。图文搜索下拉刷新继续搜索，不退回普通目录。
- 本轮沿用 1.5 视觉规范，管理端对价格、上下架和商家状态的修改会参与后续目录请求计算。

## 验证

核心测试累计 30 项，本轮新增三个业务测试：同一 SKU 的组合约束与总数；跨页全局价格排序及价格一致；商家禁用、报价到期、待审核、账号禁用、乘数舍入和手动定价生效。

`scripts/browser_filter_check.py` 在独立 126 商品/127 SKU 数据库执行六项检查：无文字预算/库存筛选，跨页全局排序，色温与预算及详情一致，零预算/重置/手机布局，相关度标识，商家正确规格报价入口。桌面与 390px 手机视口截图及结果保存本地。

`node scripts/check_miniapp_filters.cjs` 分别执行两个生成项目的首页逻辑，检查目录请求参数、零预算、搜索刷新和重置。该检查已加入 CI，只证明源码请求逻辑，不等于微信开发者工具或真机渲染验收。

## 升级

部署 1.6.0 后端与匹配的前端构建，重新生成/导入两个原生小程序。旧后端忽略新增目录参数，因此需要成套升级后才可验收新增筛选。无需数据库迁移；历史报告保留原交付快照，本轮说明及验证产物独立归档。外部服务、真实图库与真机联调项继续保留。
