# 1.3 从竞品调研到选灯与询价协同

本轮根据 [竞品调研](MARKET_RESEARCH_1_3.md) 落地，借鉴参数导购、房间项目清单和结构化 RFQ。保留本项目的客服成交与后台采购流程，没有复制竞品页面或引用其经营数字作为本项目效果。

## 已实现的变化

### 1 实际色温筛选

`GET /api/catalog/lighting-options` 返回已上架商品及 SKU 中实际存在的整数 `cct_k`，取值范围 1000—10000。缺失或无效数据不产生选项。

目录 `/api/catalog/products` 与 `/api/catalog/page` 增加可选 `cct_k`，与关键字必须命中同一 SKU，筛选后才统计和分页。返回卡片默认选中匹配色温的规格，并显示该规格价格。图片/文字搜索沿用 `attributes.cct_k` 硬条件。网页和两种原生端均提供色温选择；参数指南区分 K、W、lm，不承诺自动照明设计。

### 2 房间清单与需求预览

网页按房间分组，支持逐项勾选、只选一个房间、全选和清除选择；显示所选件数、房间金额与参考合计。客户小程序提供按房间快速选择与逐项勾选。金额均以整数分计算，运费和安装不计入参考合计。

`POST /api/inquiries/preview` 只读取数据，不创建询价。请求保持 `wishlist_ids` 和 `message`，新增可选 `requirements`：

```json
{
  "wishlist_ids": [1, 2],
  "message": "希望统一风格",
  "requirements": {
    "project_name": "客厅改造",
    "budget": 100000,
    "needed_by": "2027-01-01",
    "destination": "上海",
    "allow_alternatives": true
  }
}
```

预算以分计，日期按 UTC 当日检查不能填过去日期。期望日期是需求而非承诺；超预算只提示差额，不阻止询价协商。已下架商品会阻止提交；供货状态或参数待补充时提示客服确认。

### 3 结构化询价与不可变参考快照

提交时重新校验清单归属、商品状态和实时参考价，保存商品名称、SKU、参数、图片 ID、参考单价及数量。修改商品后不会改变已发送的询价参考信息。

新增 `inquiry_briefs` 关联表保存结构化需求和合计快照，不修改已有表的列。服务启动时 `Base.metadata.create_all` 创建此新增表；旧询价没有关联记录时返回空 `requirements` 和空 `estimate`，原流程继续可读。

客服和客户可查看需求摘要，商家不能读取客户询价。转订单时显示询价参考单价及备注，客服可调整，客户仍需确认。询价中的 SKU 即使不在客服首次加载目录内，也会作为原需求规格显示在表单中；后端仍检查实际 SKU 上架状态。

## 验证与兼容性

- 累计 22 项核心测试通过。本轮覆盖色温与规格联动、勾选和房间汇总、只读预览、预算提示、快照不随改价变化、对象权限、过期日期、下架再校验和旧询价读取。
- 本轮 6 项浏览器检查覆盖实际色温筛选、房间选择、结构化预览、提交快照、客服转单和 390px 布局，未发现 JavaScript 运行错误。
- 原有浏览器业务脚本已适配新增的“预览再确认”步骤。微信端重新生成并校验 JavaScript 语法；真实微信环境依旧待后续验收。
- 前端需配套 1.3 后端才能获取色温选项与询价预览。启动现有实例前建议使用原备份脚本备份；本轮无删表、清库或破坏性数据转换。

数据库 SQL 导出更新为 25 张表。历史课程报告保留为原版本快照，新行为以本记录为准。本轮没有训练新模型或改变采购算法，也没有用竞品宣传数字推算本项目收益。
